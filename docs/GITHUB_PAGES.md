# Единый порядок публикации Espada

Рабочая и публикуемая ветка — **main**. Сайт:
https://kringlz.github.io/espada-learning/

## Как определить версию

- release.json на сайте содержит полный коммит конкретной сборки.
- release/current — последняя успешно опубликованная версия.
- release/previous — предыдущая успешная публикация.
- release/build-<коммит> — неизменяемая точка конкретного выпуска.
- checkpoint/* — контрольные точки; АРХИВ/* — закрытые старые ветки.

Точки current и previous не записываются вручную как постоянно устаревающие
номера в README. Workflow обновляет обе метки вместе после успешного deploy.
Повторная публикация того же коммита не сдвигает предыдущую версию.

## Выпуск

Push в main или ручной запуск workflow из main выполняет проверку структуры,
типов, тесты приложения и базы на временном PostgreSQL, сборку и публикацию.
Для всех публикаций одна очередь. GitHub Pages разрешает только ветку main.
Действующая база не мигрируется этим workflow.

Архивные материалы запрещены проверкой рабочего дерева; подготовка сборки
отклоняет dist с архивом или старыми макетами. Отдельный design-lab не публикуется.
Обычный npm run build:pages лишь создаёт локальную сборку, не обновляя сайт.

Перед локальным восстановлением:

```sh
git fetch origin '+refs/tags/*:refs/tags/*'
node РЕСЕТЫ/reset.mjs list
```

Метки указывают успешные релизы, а HEAD может быть ещё не опубликован.
Если deploy успешен, но шаг записи меток завершился ошибкой, не объявляйте
весь выпуск завершённым: сверяйте release.json и повторите неуспешный job.

Подробности восстановления исходников — в РЕСЕТЫ/README.md. Старые ветки
сохранены архивными метками; не возвращайте их как параллельные рабочие ветки.
